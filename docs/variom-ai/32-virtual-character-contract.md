# VARIOM — Virtual Character Contract

**Version:** 1.0 | **Status:** NORMATIVE DRAFT — source adaptation authorized by VAR-OD-004 | **Authority:** Documents 00, 19–29.

## 1. Purpose
Defines VARIOM's concise Virtual Character Studio contract and versioned Character Sheet. It adapts the approved source concepts for VARIOM; it does not copy unrelated MAX UI or authorize code implementation.

## 2. Product principles
- Character is fictional/synthetic and belongs to one account and one brand.
- Adult-presentation baseline applies.
- Character creation must be concise and guided; reuse known brand context and avoid redundant questions.
- Character can be created, saved, edited and reused where supporting backend capability exists.
- Character is optional in relevant image/video/monthly workflows.
- Character identity and historical versions are preserved; changes do not silently rewrite running or completed work.
- Real-person likeness/voice requires documented applicable rights and consent; real-person voice imitation is not permitted without the applicable documented rights and consent.

## 3. Questionnaire structure
The VARIOM questionnaire collects only information necessary to define a coherent synthetic brand character. Its sections:
1. **Character purpose:** name/label, role in the brand and intended content use.
2. **Core identity:** fictional persona description, adult presentation confirmation and brand relationship.
3. **Visual identity:** appearance description and distinctive visual traits; optional user-provided reference material where permitted.
4. **Wardrobe and presentation:** brand-appropriate clothing/presentation preferences.
5. **Personality and behavior:** communication style, demeanor and behavioral boundaries.
6. **Language and voice direction:** Arabic/English and optional dialect/voice preference only when supported by verified capability.
7. **Consistency controls:** locked traits versus permitted variation.
8. **Review and save:** present a concise Character Sheet summary and require user confirmation before saving.

The questionnaire MUST NOT invent mandatory fields or force users to provide sensitive personal data. Optional sections may be skipped. Exact field labels and conditional validation are refined in the UX contract using approved product intent.

## 4. Character Sheet
A saved Character Sheet version records:
- character and brand identifiers;
- fictional/synthetic declaration and adult-presentation check;
- purpose/role;
- core identity and visual description;
- wardrobe/presentation;
- personality/behavior;
- approved language/voice direction where applicable;
- locked traits;
- allowed variation dimensions;
- reference assets and provenance;
- creator, version, status and timestamps;
- applicable rights/consent evidence references.

Do not store unsupported voice/model settings as if executable. Sensitive evidence is access-controlled and minimized.

## 5. Versioning and use
- Every material edit creates a new Character Sheet version.
- A task pins the exact version used.
- Existing jobs/outputs retain historical version references.
- Character selection validates account and brand ownership.
- Deleting a character follows the governed deletion lifecycle and does not bypass retention obligations.
- A character may be marked inactive; inactive characters cannot be selected for new tasks but historical outputs remain traceable.

## 6. Consent, safety and rights
- Do not create or use a real person's likeness/voice without applicable documented rights and consent.
- No deceptive synthetic testimonial presented as a genuine real-customer statement.
- Do not use character features to evade provider policy or safety controls.
- Reference uploads are private, validated and processed under Document 27.
- Voice/dialect/lip-sync are hidden or unavailable unless the provider register verifies capability, rights, region and data terms.

## 7. Acceptance criteria
- Questionnaire and Character Sheet are VARIOM-specific and concise.
- Character is fictional/synthetic, adult-presenting and brand-bound.
- Locked traits and permitted variations are explicit.
- Version history is preserved and tasks pin versions.
- Consent/rights and provider gates are enforced.
- Unsupported voice/dialect/lip-sync controls are not shown.
- Save/edit/reuse claims require real persistence evidence.
